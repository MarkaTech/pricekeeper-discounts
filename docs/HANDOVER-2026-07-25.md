## 1. What this app is

Discountify (App Store listing name: **"Discountify: Volume & BOGO"**) is a Shopify discount app owned by MARKA MODERN RETAIL PRIVATE LIMITED. Its entire competitive identity is one architectural promise: **it never edits a product price.** Every discount — percentage, fixed amount, new price, volume/quantity breaks, BOGO, cart-total, free shipping — is computed at checkout by a native Shopify Function. The main competitor, Discounty, edits real catalog prices to fake sales, which corrupts catalogs and leaves wrong prices behind after uninstall. Discountify structurally cannot do that: the only writes it ever makes to a store are its own automatic discount records and four small metafields (two for the discount function, two for storefront display widgets).

- **Repo:** github.com/MarkaTech/pricekeeper-discounts (branch `main`)
- **Stack:** Remix + Vite + TypeScript · Prisma (SQLite in dev) · Polaris + App Bridge v4 · one Shopify Function extension · one theme app extension
- **Partner org:** MARKA MODERN RETAIL PRIVATE LIMITED · **Dev store:** discountify-test-uww1aktk.myshopify.com

### b. Analytics page (commit `ffb7c94`)

### c. Widgets page + a silent-failure fix (commit `ffb7c94`)
`/app/widgets` — toggles for all five storefront widgets (price badge, tier table, BOGO badge, countdown, free-shipping bar) plus an accent color.
**Important find:** the code that publishes widget data to the storefront existed but was never called from anywhere — meaning storefront widgets could never have displayed anything. Publishing is now wired into every widget save and every campaign activate/pause/delete.

### d. Campaign management (commit `031f613`)
Campaigns can now be **edited** (full form; editing a live campaign pushes the change straight to its Shopify discount), **paused**, and **deleted** (confirmation dialog; also removes the Shopify discount record). Previously only create/activate existed.

### e. Campaign builder rebuilt (commit `031f613`)
The raw JSON text boxes are gone. The builder now has real product and collection pickers (Shopify's native picker dialog), add/remove rows for volume tiers ("buy 3 → 10% off, buy 5 → 15% off"), and proper fields for BOGO (buy quantity, get quantity, discount on the free items, max repeats per cart).

### f. The critical bug this session caught (commit `031f613`)
The old builder saved campaigns in a format the checkout engine **silently rejects** — the engine is deliberately fail-closed (bad config = no discount, never a crash), and the old UI's output was "bad config." **Every campaign created before 25 July 2026 would have applied zero discount at checkout.** The new builder always emits engine-valid data, the server now refuses to save anything else, and the admin-side rules were aligned with the engine (they previously disagreed about BOGO's format). Any campaign created before this date must be recreated or re-saved.

### g. Missing webhook handlers (commit `ffb7c94`)
Three webhook topics were registered with Shopify but had no receiving code (deliveries would have failed): `app_subscriptions/update`, `app/scopes_update`, `shop/update`. All three handlers now exist.

### h. Repo hygiene after a bad push (commit `f11450a`)
A push from the cloud workspace accidentally included dependency lockfiles pinned to older package versions, which broke `git pull` on the owner's Mac and could have downgraded packages. Fixed by untracking lockfiles repo-wide with an explanatory note in `.gitignore`. Rule going forward: **never commit a lockfile from the cloud sandbox**; regenerate one on the deploy machine before production.

## 8. How to run and work on this project (the traps, so nobody rediscovers them)

- **Dev server** runs only on the owner's Mac: `shopify app dev --use-localhost` in the project folder (the plain Cloudflare-tunnel mode is flaky here). If it dies with *"Unable to update lock within the stale threshold"*: run it again; if it repeats, `rm -rf .shopify` and run again (re-asks for the Mac password once for the localhost certificate). Success looks like a persistent screen with `(d) Dev status | (a) App info | (q) Quit` at the bottom. Note: `--use-localhost` can't deliver webhooks — webhook testing needs tunnel mode or a deployed host.
- **Browser testing** happens in the owner's Chrome. Shopify's account chooser defaults to the **live Divine Hindu store's account** — always pick "Admin Shapify / care.shapify@gmail.com" for the dev store.
- **Never test anything on the live Divine Hindu store.** The Shopify connector in Claude is bound to it; dev-store work goes through the browser only.
- **Code transport:** cloud workspace → GitHub → owner's Mac (`git pull`). Each push needs a fresh throwaway GitHub token the owner creates and revokes right after. Never commit lockfiles from the cloud side.
- **Cloud-sandbox quirk:** a fresh `npm install` there resolves older Shopify packages than the Mac has, producing a handful of TypeScript errors that are environment noise (`ApiVersion.January26`, Polaris CSS import, a few implicit-any warnings in untouched files). The trustworthy checks in the sandbox are `remix vite:build` and the engine test suite (`npx vitest run --config /dev/null` inside `extensions/discount-function`).
- The five discounts sitting on the dev store (CODE_BXGY…, FREESHIPPING2026, …) are leftovers made natively during earlier sessions — not app campaigns; ignore or delete.
- **At the time of writing, commits `9e13167` and `3a795a0` are local to the cloud workspace and not yet pushed** — the next push (needs a token) carries the listing docs, decisions, and final icon to GitHub.
